Multi-Account AWS Governance

Secure AWS Landing Zone Architecture for Enterprise Workloads

Designed a multi-account AWS environment to establish stronger security boundaries, centralized governance, logging and operational control across enterprise workloads.

Project Overview

Designed a multi-account AWS environment based on the principle of separating workloads according to their operational and governance requirements.

The architecture separates development, production, shared services and centralized logging into dedicated AWS accounts, creating clear security and operational boundaries while providing a foundation for centralized governance.

4 Accounts Dedicated workload and governance boundaries
Centralized Logging Dedicated account for audit and log management
Governed Security, identity and operational controls

Business Challenge

As organizations expand their use of AWS, placing all workloads inside a single account can make security, access management, billing visibility and operational governance increasingly difficult.

Different environments also have different risk profiles. Development workloads require flexibility for experimentation, while production environments require stronger controls and tighter access boundaries.

The objective was therefore to establish an AWS structure that could support workload growth while improving isolation, governance, security visibility and operational control.

Architecture Approach

The architecture uses separate AWS accounts as the primary isolation boundary. Each account has a defined purpose, while shared governance and security capabilities provide centralized oversight.

High-Level Structure AWS Organization → Development Account | Production Account | Shared Services Account | Centralized Logging Account

This structure allows environments to be managed independently while maintaining consistent organizational governance and security practices.

Development Account

The development account provides an isolated environment for application development, testing and experimentation.

Separating development resources from production reduces the risk of development activities unintentionally affecting production workloads.

The account can therefore provide developers with the flexibility required to build and test applications while maintaining a separate production security boundary.

Production Account

The production account contains business-critical workloads and operates under stricter access and operational controls.

Production resources are isolated from development activities, reducing the potential blast radius of configuration errors, unauthorized access or accidental changes.

Access is controlled through appropriate IAM roles and permissions, with operational activity subject to centralized monitoring and auditing.

Shared Services Account

The shared services account provides infrastructure and services that may need to be consumed across multiple workload accounts.

Centralizing appropriate shared capabilities reduces unnecessary duplication while keeping common infrastructure separate from individual application workloads.

Access to shared resources is controlled through explicit permissions and defined trust relationships between accounts.

Centralized Logging Account

A dedicated centralized logging account provides a separate security boundary for audit and operational log data.

Keeping logs outside individual workload accounts reduces the likelihood that application administrators can modify or remove the evidence needed for centralized monitoring and investigation.

This approach strengthens auditability and provides a consistent location for reviewing activity across the AWS environment.

Identity & Access Management

Identity was treated as a core component of the landing zone architecture.

IAM roles and policies are used to establish controlled access to resources, with permissions aligned to the responsibilities of users, applications and operational teams.

  • Least-privilege permissions for workload access.
  • Separation of administrative responsibilities.
  • Controlled cross-account access where required.
  • Reduced reliance on broad permissions across the environment.
  • Clear separation between development and production access.

Security & Governance

Account Isolation

Dedicated AWS accounts establish security boundaries between workloads and environments, helping limit the potential blast radius of security or configuration incidents.

Centralized Visibility

Centralized logging provides visibility across accounts and supports security investigations, operational troubleshooting and audit requirements.

Controlled Access

IAM policies and roles provide granular control over which users and workloads can access resources within and across accounts.

Governance at Scale

Establishing the account structure early creates a foundation for applying consistent governance as additional workloads and accounts are introduced.

Networking & Shared Connectivity

Multi-account environments require deliberate consideration of how workloads communicate with shared services and other accounts.

The architecture therefore treats cross-account connectivity as a controlled requirement rather than allowing unrestricted communication between environments.

Where connectivity is required, access can be established through explicitly defined networking paths, security controls and appropriate routing boundaries.

Technical Challenges & Solutions

Balancing Isolation With Collaboration

Separating accounts improves security but can make it more difficult for workloads to consume common services.

The architecture addresses this by placing appropriate shared capabilities in a dedicated shared services account and defining controlled access between accounts.

Centralizing Logs Without Weakening Security

Logging information should remain accessible for investigation while being protected from unnecessary modification by workload administrators.

A dedicated centralized logging account provides stronger separation between workload administration and audit information.

Managing Cross-Account Access

Cross-account access introduces additional trust relationships and must therefore be deliberately controlled.

IAM roles, explicit permissions and defined access paths are used to ensure that cross-account access is granted only where required.

Designing for Future Growth

A landing zone should not only support the workloads that exist today. It should provide a structure that can accommodate additional applications, environments and AWS accounts.

Separating workloads by account establishes a scalable foundation for future expansion and more granular governance.

Governance Model

The architecture establishes governance across four primary dimensions:

  • Account: Workloads are separated according to environment and responsibility.
  • Identity: Access is controlled through IAM roles and least-privilege permissions.
  • Visibility: Logging and monitoring provide centralized operational and security insight.
  • Connectivity: Cross-account communication is treated as an explicit and controlled requirement.

Outcome

The resulting landing zone architecture established a stronger foundation for operating enterprise workloads on AWS while improving isolation, governance and security visibility.

  • Established dedicated development and production security boundaries.
  • Created a shared services environment for common infrastructure capabilities.
  • Established a centralized logging environment for audit and operational visibility.
  • Improved control over identity and cross-account access.
  • Reduced the potential blast radius of workload-level security or configuration incidents.
  • Created an AWS foundation that can support additional workloads and accounts as the organization grows.
